## 0. Головне за 1 хвилину

- **Тариф «Швидкий» (найдешевший віртуальний хостинг) підходить** для схеми «статичний сайт + WordPress на піддомені `cms.` + PHP-обробник форм»: 10 GB NVMe, 1 сайт (піддомени не рахуються як сайти, до 999), 512 MB RAM, PHP до 8.5, MySQL 8.4, SSH з ключами, Git, cron (≥1 хв), WP-CLI, Let's Encrypt, щоденні бекапи. Ціна **від 226 ₴/міс** (за передоплати на 3 роки, знижка 34 %), **345 ₴/міс** без знижки. [✔ джерело 1, 2]
- **Розташування сервера можна вибрати: Україна, Німеччина, Польща, Франція, Фінляндія…** (зміна країни акаунта в панелі). **Рекомендація: Німеччина** (ЄС, близько до клієнтів у DE). Компанія-провайдер українська (ТОВ «Хостінг Україна»), а для України **немає** рішення ЄС про адекватність, тому DPA/SCC — питання до юриста. [✔ джерело 2, 3, 13]
- **Критична знахідка: домен `osta-trading.com` УЖЕ ІСНУЄ** (зареєстрований 2015-08-07, реєстратор Key-Systems, NS `domainit.de`, продовжений до 2027-08-07). На ньому працює **старий сайт WordPress 5.3.27 + WooCommerce 3.9.5** (застарілі, вразливі версії) з ≈130 URL у sitemap, а **пошта компанії** працює через `mx*.europeanmx.eu` (SPF `include:spf.webwide.net`). Тобто запуск означає **міграцію з картою 301-редиректів і збереженням MX**, а не новий домен. Потрібне рішення замовника (питання №1). [✔ dig/whois/curl 2026-11-13]
- **Рекомендована схема:** WordPress лише як headless-адмінка каталогу (CPT «Інгредієнт» у власному MU-плагіні) → кнопка/подія в WP → GitHub Actions (`workflow_dispatch`) → `fetch-from-WP` → `npm run build` → гейти → деплой статики на хостинг (rsync по SSH-ключу) → пост-деплой перевірки → автовідкат. Форми обробляє окремий PHP-скрипт на основному домені, без WP.
- **Що потрібно від замовника:** рішення щодо домену, оплата хостингу (робить сам), доступ до DNS, делегування хостинг-акаунта, GitHub Secrets (додає сам), Google-акаунт для GSC/GA4, адреси для форм, юрист для GDPR/Impressum (розд. 4).
- **Обсяг:** 11 етапів (P0–P10), ≈38 задач; P0 (без доступів) можна робити вже зараз паралельно з дизайном.

### 1.3 Висновок щодо тарифу

- **Вистачає** [~ ймовірно]: статика ≈11 MB (`dist/`, з них three.js 560 kB), WP-адмінка з кількома редакторами й ~200 записами, PHP-форми. Навантаження від WP мінімальне, бо публічний трафік іде на статичні файли через nginx.
- **Межа 1 сайту:** `cms.<домен>` і `staging.<домен>` є піддоменами того самого сайту, тому вміщуються [~ ймовірно, 20]. Окремий домен для staging зайняв би другий «сайт» і вимагав би тарифу «Кращий».
- **Може знадобитися докупити:** OPcache для WP (для швидкості адмінки; не критично); підвищені ліміти листів (якщо форм > 500/добу, малоймовірно); «Кращий» (якщо потрібен окремий акаунт для ізоляції WP від статики, див. 3.1).
- **GDPR / затримки:** вибрати при замовленні **Німеччину**. Для клієнтів у DE затримка мінімальна, дані в ЄС. Водночас провайдер є українською компанією (не ЄС, адекватності немає), тож потрібні DPA + SCC або інша підстава: **питання до юриста**. Альтернатива для порівняння (не замість вибору замовника): німецькі хостери з DPA за GDPR «з коробки». Статику можна додатково віддавати через Cloudflare (теж DPA).

## 2. Архітектура

```
 Редактор ──► cms.<домен> (WordPress, noindex, 2FA)
                 │ save/publish → дебаунс 2 хв → POST workflow_dispatch (токен: Actions:write лише на repo osta)
                 ▼
 GitHub Actions "release.yml":
   npm ci → fetch-from-wp (REST, app-password read-only) → валідація схеми JSON
   → npm run build (siteUrl=https://<домен>) → audit:seo + гейти → artifact
   → deploy: rsync по SSH-ключу у ~/<домен>/releases/<sha> → перемикання → postdeploy smoke
   → FAIL? автоматичний відкат на попередній реліз + issue/лист
                 ▼
 https://<домен>/  (nginx-статика; /api/form.php → PHP → SMTP)
```

### 2.1 (а) WordPress як headless-адмінка

- **Розміщення:** `cms.<домен>` (окремий кореневий каталог `~/<домен>/cms`). Не `/cms/`: інакше WP-правила `.htaccess` і cookies змішуються зі статикою, і шлях потрапляє в публічний сайт.
- **Тип запису «Інгредієнт»** (`osta_ingredient`) реєструє **власний MU-плагін `osta-catalog`** (код у репозиторії `wp/mu-plugins/osta-catalog/`, без ACF: менше залежностей і вразливостей; ACF Free лише якщо редакторам потрібен зручніший UI. Рішення: P3).
- **Поля** (мапа на `products.json` / `product-details.json` / `seo/pages.json`; див. `content/seo/data-model.md`):

| Поле | Тип | Примітка |
|---|---|---|
| `name`, `slug` | заголовок + slug WP | slug незмінний після публікації (зміна дає 301 через карту `redirects`) |
| `inn`, `cas`, `formula`, `molecular_weight`, `pharmacopoeia`, `appearance`, `grade` | text | CAS з валідацією формату й контрольної цифри |
| `description_en`, `description_de`, `usage_en`, `usage_de` | textarea (без HTML або з обмеженим набором) | DE може бути порожнім: на DE-сторінці тоді немає дубля EN-тексту (поточне правило) |
| `categories` | таксономія `api / excipients / food-grade` (+ терапевтичні групи) | |
| `synonyms` | повторюване текстове поле | |
| `documents` | вкладення PDF (медіа WP) | у збірці копіюються в `dist/docs/<slug>/`, щоб публічний сайт не залежав від `cms.` |
| `availability` | `in_stock / on_request / hidden` | |
| `seo_ready` | авто, лише для читання | розраховується на `save_post` за гейтом `site.config.json → productGate` (≥ 2 факти, ≥ 40 слів); редактор бачить, чого бракує |
| `seo_title_*`, `seo_desc_*` | необов'язкові override | ліміти 30–60 / 70–160 перевіряє UI і `audit:seo` |
| `updated_at` | авто (`post_modified_gmt`) | |

- **Статичні сторінки** (Home/About/Services) у першій версії лишаються в git (`src/i18n/*.json`). Перенесення текстів у WP — окрема задача, якщо замовник захоче (питання №6).
- **REST:** публічний REST для анонімів вимкнено (`rest_authentication_errors`), крім того, що потрібно ядру. Власний маршрут `osta/v1/export` (лише GET) повертає готовий JSON для збірки. Доступ: технічний користувач `ci-reader` з власною роллю (одна capability `osta_export`) + **Application Password** (зберігається лише в GitHub Secrets). Додатково: заголовок-ключ або IP-обмеження недоречні, бо IP GitHub-раннерів динамічні.

### 2.2 (б) Конвеєр WP → збірка → деплой

1. **Тригер:** MU-плагін на `save_post/trash/untrash` для `osta_ingredient` ставить `wp_schedule_single_event(+120 с)` (дебаунс серії правок) → `POST /repos/Mak-nw/osta/actions/workflows/release.yml/dispatches`. **`workflow_dispatch` замість `repository_dispatch`**, бо fine-grained токену потрібен лише дозвіл **Actions: write** (а для `repository_dispatch` потрібен Contents: write, тобто право писати в репозиторій) [~ ймовірно, 25]. Токен fine-grained, лише репозиторій `osta`, термін ≤ 1 рік, зберігається в `wp-config.php` поза веб-коренем (`define` з файлу `~/secrets/osta.php`, права 600), не в БД.
   - Резерв: розклад `schedule: '*/30 * * * *'` у workflow порівнює `osta/v1/export?since=` і збирає, лише якщо є зміни (працює, навіть коли webhook не дійшов).
   - Кнопка «Опублікувати сайт зараз» в адмінці + сторінка статусу (останній run: OK/FAIL, час).
   - WP-Cron вимкнути (`DISABLE_WP_CRON`), натомість cron хостингу кожні 5 хв: `wp cron event run --due-now` (WP-CLI є) [✔ 11, 12].
2. **Workflow `release.yml`** (новий; `deploy.yml` для GitHub Pages лишається як staging/redirect, див. 2.4):
   - `concurrency: release` (без паралельних деплоїв), `permissions: contents: read`.
   - `npm ci` → `node tools/fetch-from-wp.cjs` (пише `src/data/products.json`, `product-details.json`, доповнює `seo/pages.json`; **валідація JSON-схеми**, слаги, дублікати, різке падіння кількості позицій > 20 % = FAIL, захист від порожньої відповіді) → `npm run build` → `npm run audit:seo` → артефакт `dist.tar.gz` + `sha256`.
   - Дані з WP **не комітяться в main автоматично** (щоб не засмічувати історію й не давати CI права на запис). Знімок JSON зберігається як артефакт релізу (на 90 днів) для аудиту й відкату.
3. **Деплой** (job `deploy`, `environment: production` з **ручним схваленням для першого запуску**, далі автоматично):
   - SSH-ключ ed25519 **лише для деплою** (`DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` у GitHub Secrets; `known_hosts` закріплений, без `StrictHostKeyChecking=no`).
   - `rsync -a --delete` у **`~/<домен>/releases/<sha>/`**, потім перемикання. Варіанти перемикання (вибір на P2 після тесту):
     - **A (рекомендовано):** кореневий каталог сайту = `www/` (звичайний каталог, бекапи працюють). Розкладка: `rsync --delay-updates` спершу хешованих `assets/`, потім HTML (майже атомарно; старі хеш-асети видаляються лише через 3 релізи, тож відкриті сторінки не ламаються). Відкат: `rsync` з `releases/<prev>/` (≈секунди).
     - B: перемикання кореневого каталогу через API хостингу між `www-a/` і `www-b/` (атомарно, але залежить від API-токена з правами на весь акаунт) [? гіпотеза].
     - ✗ Симлінк `www → releases/x`: **ламає автоматичні бекапи сайту** [✔ 18]. Не використовувати.
   - Зберігати **5 останніх релізів** у `releases/`.
4. **Після деплою:** `npm run postdeploy -- https://<домен>` (smoke-набір з розд. 5, ≈1 хв). FAIL = автоматичний відкат + повідомлення (GitHub issue + лист на технічну адресу).
5. **Альтернатива без SSH-ключа в GitHub (pull-модель)** [? гіпотеза, розглянути на P4]: workflow публікує GitHub Release з `dist.tar.gz`, `sha256` і підписом `ssh-keygen -Y sign`; cron на хостингу щохвилини перевіряє останній реліз, звіряє підпис публічним ключем і розгортає. Плюс: у GitHub немає облікових даних до хостингу. Мінус: складніше, затримка ≤ 1 хв, cron-скрипт стає точкою ризику.

### 2.3 (в) Форми (Contact, Inquiry, Request quotation/documentation)

Зараз форма `contact.html` має mock-submit (`src/pages/contact.js`, TODO на `/api/contact`).

**Рекомендація: власний PHP-обробник `/api/form.php` на основному домені (той самий origin, без CORS), незалежний від WordPress.**

| Критерій | PHP-обробник (рекомендовано) | WP-плагін (Fluent Forms / CF7) |
|---|---|---|
| Залежність від WP | немає: форми працюють, навіть якщо `cms.` вимкнено / зламано / закрито IP | WP має бути публічно доступним; `cms.` перестає бути «закритою» адмінкою |
| Поверхня атаки | ≈200 рядків, рев'ю повністю | плагін + його оновлення й CVE |
| Статика | звичайний `fetch` того самого origin | CORS + REST/AJAX на інший піддомен, cookies |
| Зберігання ПД | за замовчуванням не зберігає (лише лист) | зберігає записи в БД, тому треба ще й чистити |
| Зручність перегляду заявок | лише пошта | список у WP |

Вимоги до обробника:
- POST лише JSON/form-data; ліміт розміру; whitelist полів за типом форми (`contact | inquiry | quote | docs`); серверна валідація (email, довжини, `product` slug із поточного `products.json`); санітизація; захист від header injection (жодних CR/LF у `From/Subject`, `Reply-To` = адреса користувача, `From` = скринька домену).
- Антиспам **без трекінгу**: honeypot-поле, time-trap (≥ 3 с від рендеру, підписаний HMAC-токен із часом), rate-limit за IP (хеш IP + сіль, TTL 24 год, файл/SQLite поза веб-коренем), ліміт за email. Якщо спаму забагато, вмикається proof-of-work ALTCHA (self-hosted, без третіх сторін) [~ ймовірно]. Cloudflare Turnstile / hCaptcha лише як запасний варіант: це передача даних третій стороні, тож потрібна згадка в Datenschutz.
- CSRF: класичного сеансу немає, тому HMAC-токен форми + перевірка `Origin`/`Referer` = свій домен.
- Відправлення: **автентифікований SMTP (465/TLS)** [✔ 16]. Бажано через **існуючого поштового провайдера домену** (europeanmx/webwide), бо SPF уже налаштований на нього, або через `mail.adm.tools` (тоді додати хостинг у SPF і DKIM). Облікові дані SMTP лежать у `~/secrets/form.php` (поза `www`, 600), **не в git**.
- Лист менеджеру (адреси від замовника; за типом форми / продуктом) + **автовідповідь користувачу** (без повтору всього введеного тексту, щоб форма не стала спам-ретранслятором).
- GDPR: обов'язковий checkbox згоди з посиланням на `privacy.html` / `data-processing.html` (EN/DE), текст згоди й версія політики в листі; за замовчуванням **нічого не зберігати на сервері** (лише лист). Логи без тексту повідомлення.
- Доступність: `aria-live` для помилок, фокус на першій помилці, працює з клавіатури; без JS форма відправляється звичайним POST і отримує HTML-відповідь (PRG-редирект на `?sent=1`).
- `noindex` і `Disallow: /api/` у robots.

### 2.4 (г) Домен, DNS, SSL, редиректи, заголовки

- **Канонічний хост:** апекс `https://<домен>/` (поточний старий сайт теж на апексі: `www` → апекс). `www` → апекс 301; HTTP → HTTPS 301 (налаштування панелі [✔ 15]); один стрибок, без ланцюжків.
- **HSTS:** після стабільного тижня `max-age=31536000; includeSubDomains`; preload лише за рішенням замовника (незворотно на місяці).
- **`site.config.json → siteUrl`** = `https://<домен>`. Від нього залежать `VITE_BASE=/`, canonical, hreflang, sitemap, robots, OG і JSON-LD (вже реалізовано). Workflow для продакшну збирає з `VITE_BASE=/`.
- **`robots.txt`** у корені домену (на GH Pages у підкаталозі він не діє: про це вже є коментар у `seo/core.js`). `cms.` і `staging.` мають власні `robots.txt` з `Disallow: /` **плюс** `X-Robots-Tag: noindex, nofollow` (саме по собі `Disallow` не прибирає URL з індексу).
- **Міграція старого `osta-trading.com`** (якщо домен той самий, див. 0): вивантажити всі ≈130 URL старих sitemap (`post/page/product/product_cat/attachment/...`) + звіт «Сторінки» з GSC (якщо є доступ) → `redirects.csv` (старий URL → новий, 301; без відповідника → найближчий хаб або 410). Генерувати з нього `.htaccess` (`RewriteRule`). Старий WP після переїзду **вимкнути й видалити** з хостингу провайдера (WP 5.3 + WooCommerce 3.9 вразливі), попередньо зробивши архів.
- **Старий `mak-nw.github.io/osta/`:** GitHub Pages не вміє 301 на чужий домен. Тому `deploy.yml` перебудувати на «redirect stubs»: кожна стара URL віддає HTML з `<link rel=canonical>` на новий домен + `<meta http-equiv="refresh" content="0;url=…">` + `location.replace`. Google розглядає миттєвий meta refresh як постійний редирект [~ ймовірно, 30]. Staging переїжджає на `staging.<домен>`.
- **404:** справжній статус 404 (`ErrorDocument 404 /404.html`; у панелі є налаштування власної 404 [✔ 21]); прихована позиція (`hidden`) → **410** (`.htaccess` генерується з переліку прихованих slug'ів).
- **`.htaccess`** (генерується збіркою з шаблону `deploy/htaccess.tpl`):
  - кеш: `assets/*` з хешем → `Cache-Control: public, max-age=31536000, immutable`; HTML → `no-cache`; sitemap/robots/llms → 1 год.
  - стиснення: gzip (mod_deflate); brotli, якщо є (не підтверджено); на nginx-статиці стиснення й кеш дають налаштування панелі «Статичні файли / Expire» [✔ 5].
  - **security headers:** `Content-Security-Policy` (`default-src 'self'; img-src 'self' data:; script-src 'self' + GA-домени після згоди; connect-src 'self' + GA; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`.
  - **Ризик [? гіпотеза]:** якщо `.html` у списку статики nginx, заголовки з `.htaccess` на HTML не потраплять. Рішення на P2: (1) прибрати `html` зі списку статики (HTML віддає Apache, асети nginx); або (2) задати заголовки через панель (HSTS є [✔ 15]); або (3) CSP через `<meta http-equiv>` як резерв (без `frame-ancestors`). Перевірка: `check-headers` (розд. 5).
  - hotlink-захист для `/docs/*.pdf` і `assets/img` (за `Referer`, з дозволом порожнього Referer) [~ ймовірно].
- **DNS (у замовника або в провайдера домену):** `A/AAAA` апекса й `www` → IP хостингу; `cms`, `staging` → той самий хост; **MX і поштові TXT не чіпати** (поточна пошта: europeanmx.eu); додати SPF/DKIM/DMARC для відправника форм; `CAA` на `letsencrypt.org`. TTL знизити до 300 с за 48 год до перемикання.

### 3.1 WordPress hardening (чекліст)

- [ ] Остання стабільна версія WP, PHP 8.3+, MySQL 8.4; автооновлення ядра (minor + major після 7 днів), плагінів (лише з переліку).

- [ ] REST: анонімам заборонено (крім потрібного ядру); `users`-ендпоінт закрито; author-archives вимкнено (немає енумерації логінів).

Натомість WAF-правило хостингу «лише країни DE/UA (+ країни менеджерів)» на `cms.` [✔ 19] і, за бажання, Basic Auth на `/wp-admin` і `/wp-login.php`.

## 7. Ризики й питання до замовника

### Ризики

| Ризик | Вплив | Рішення |
|---|---|---|
| `osta-trading.com` уже має старий сайт і пошту | втрата позицій у Google, **зупинка пошти** при помилці DNS | карта 301; MX/TXT не чіпати; зміни DNS лише за diff + «так»; TTL 300 перед cut-over |
| Старий WP 5.3 / WooCommerce 3.9 вразливий | компрометація домену, спам від імені компанії | після міграції архівувати й вимкнути |
| Провайдер не з ЄС, адекватності немає | GDPR-ризик | локація DE + DPA/SCC + юрист; або ЄС-хостер |
| `.htaccess` не діє на nginx-статику | немає CSP/кешу на HTML | тест на P2, варіанти в 2.4 |
| SSH-ключ = доступ до всього акаунта | компрометація CI зачіпає WP | окремий environment з ключем; опційно окремий хостинг-акаунт для WP; pull-модель |
| 3D (three.js) знижує mobile-PageSpeed | < 90 | poster + lazy + умови пристрою (5.г) |
| Ліміт 500 листів/добу | бот-атака вичерпує ліміт | rate-limit + honeypot; моніторинг |
| Токени спливають (API хостингу 6 міс, GitHub ≤ 1 рік) | збірка/webhook зупиняються | нагадування + щотижневий health-check |
| Брак DE-контенту в WP | тонкі DE-сторінки | DE-продукти не генеруються (поточне правило) |

### Питання до замовника (≤ 10, через форму `questions/`)

1. **Домен:** запускаємо на існуючому `osta-trading.com` (замінюємо старий WP-сайт, зберігаємо пошту) чи на новому домені? Хто має доступ до реєстратора/DNS (`domainit.de` / Key-Systems)?
2. **Тариф і ізоляція:** «Швидкий» (≈226–345 ₴/міс) з WP і сайтом в одному акаунті, чи 2 акаунти (сайт окремо від WP, ×2 ціни) для суворішої безпеки?
3. **Локація сервера:** Німеччина (рекомендовано для GDPR і клієнтів у DE) чи Україна?
4. **Форми:** на які адреси надсилати кожен тип форми? Відправляти через поточного поштового провайдера (рекомендовано) чи через пошту хостингу? Зберігати копії заявок на сервері (за замовчуванням ні)?
5. **Аналітика й боти:** GA4 у режимі basic (нічого до згоди, рекомендовано) чи advanced? Дозволяти AI-ботам навчання (`aiTrainingBots: allow`, як зараз) чи лише AI-пошук?
6. **Контент у WP:** лише каталог інгредієнтів чи й тексти сторінок (About/Services)? DE-описи продуктів пишуться (і ким) чи продукти лишаються лише EN?
7. **Хто наповнює:** імена й email менеджерів для WP; хто відповідає за INN/CAS/PDF і номери EudraGMDP/WDA/GDP?
8. **Публікація:** зміни з WP одразу на сайт (≈10 хв) чи через перегляд на staging і кнопку «Опублікувати»?
9. **Бюджет на дрібні послуги:** OPcache, Cloudflare (Free), uptime-монітор (Free), окремий хостинг для WP: що погоджено?
10. **Юрист:** хто перевіряє Impressum/Datenschutz/cookie-тексти і DPA з хостингом, і до якої дати?
